# Attack report

Generated by `gradle attackDemo` against the in-process service, through the real signed
envelope path. Reproduce with:

```bash
gradle attackDemo
```

Probes A1–B3 target the *format and parameter conversion* class the audit named. C1–C4
target *batch probing*. D1–D7 target the protocol around the primitives (replay, forgery,
error oracles, offline formats, database access).

## Reading the report

- **BLOCKED** — the attack did not produce a PIN or a usable oracle.
- **CONTROL** — a probe that is *supposed* to succeed, included to state residual risk
  honestly rather than claim a guarantee that does not exist.

## Notes on selected probes

### A1 — parameter injection

Four requests, each adding exactly one field the operation does not declare (`pvki`,
`verificationKeyId`, `decimalizationTable`, `maxTries`). All are rejected at JSON parse time
because the codec fails on unknown properties. The follow-up baseline request in the same
probe succeeds, proving the rejection is the schema and not a broken request.

### B1 — the conversion oracle

The attacker holds an ISO-1 block (no PAN inside it) and presents it for three different
accounts. Only the card whose live terminal session signed the binding assertion could ever
succeed, and that assertion is an HMAC over `sessionId‖accountId‖expires` with a key used for
nothing else. This is the control that makes an unbound format survivable at all.

### C1 / C2 / C3 — batch probing

C1 shows the budget is exhausted after 3 failures (`4 attempts` includes the one that trips
the lock). C2 shows three distinct credentials share the same counter, because the ledger is
keyed by account. C3 shows that 24 concurrent requests do not get 24 comparisons: the attempt
is reserved under a lock *before* the PIN is compared, so concurrent requests observe the
lockout.

### C4 — the control that succeeds

This is the most important line in the report. A PVV is a 4-digit function of the PIN. Given
the PAN and the PVV, the PIN falls out of a 10⁴ enumeration with no HSM involved. Nothing in
this service can prevent that once the PVV is disclosed. What the service does instead is
refuse to be an *oracle*: there is no endpoint that computes a PVV for a caller-supplied PIN,
disclosure needs a second officer's ticket, and every disclosure is logged. The residual risk
is a policy and key-management problem, not an API problem, and pretending otherwise would be
the actual vulnerability.

### D5 — error oracle

21 masks: truncation, over-length, non-hex, reversal, and a 16-way last-byte walk. The
observed codes are only `PIN_BLOCK_INVALID` and `CARD_LOCKED`. A service that answered
"padding error" to one mask and "wrong PIN" to another would leak the plaintext structure of
the block; this one does not.

### D7 — database access

A direct field read of `card.pvv`. An API cannot protect a value that also lives in a table
the attacker can read. The mitigations that do apply are listed in the probe output: dual
control on disclosure, the verifier never crossing the API, and the audit chain recording
every disclosure.
